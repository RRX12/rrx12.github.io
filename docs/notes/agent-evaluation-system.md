## 前言：从一次评测到持续演进

在上一篇《[Agent 评测（一）：从评测设计到问题定位](/notes/agent-evaluation)》中，我主要讨论了 Agent 评测的基础方法：如何定义评测目标、设计 Metrics 和 Rubric、构建评测集，以及通过评测结果和执行过程定位问题。

但对于一个真正投入业务使用的 Agent 来说，完成一次评测只是起点。随着业务数据、用户需求和系统能力不断变化，原有评测集可能逐渐失去代表性，新的问题也会不断出现。如果每次优化都依赖人工发现问题、分析原因、修改 Prompt，再重新测试，就很难形成稳定、可复用的优化机制。

因此，评测不应该只是一个独立的测试环节，而应该是一套能够持续运行的系统。

这套系统的核心是**评测资产**。它不仅定义 Agent 应该具备什么能力，还需要持续沉淀真实运行中的问题、验证过的解决方案和业务质量标准。通过离线评测、在线反馈、Case 挖掘与归因，将这些资产不断反哺 Agent 和评测体系本身。

本文将以企业招投标机会智能筛选系统为例，讨论如何从初始评测资产建设开始，逐步建立离线验证、线上反馈、问题归因和自动化优化机制，让每次运行产生的经验都能够成为下一轮优化的依据。

## <span class="chapter-number">01.</span> Agent 评测系统的整体架构

一套可持续运行的 Agent 评测系统，可以概括为：

**四个模块、三种能力、两条 Loop、一套评测资产。**

这四个部分不是简单的概念组合，而是分别回答评测系统由什么组成、需要具备什么能力、如何持续运转，以及最终沉淀什么。

### 1.1 四个核心模块：系统由什么组成？

<div class="table-scroll" role="region" aria-label="模块、核心作用、解决的问题（可横向滚动）" tabindex="0">

| 模块 | 核心作用 | 解决的问题 |
|---|---|---|
| 离线评测 | 使用固定评测资产验证 Agent 版本 | 已知问题是否解决？是否引入新的退化？ |
| 在线评测与监控 | 观察真实业务中的质量与运行状态 | 线上运行是否正常？是否出现新的问题？ |
| Case 挖掘与归因 | 将异常信号转化为可分析的案例 | 问题发生在哪里？应该优化什么？ |
| Agent 观测基建 | 记录 Agent 完整执行过程 | 能否还原问题发生的具体环节？ |

</div>

四个模块承担不同职责：

- 离线评测负责版本变更后的回归验证和发布门禁。
- 在线评测与监控负责持续观察真实业务中的质量和运行状态。
- Case 挖掘与归因负责将异常转化为具体问题，并定位根因。
- 观测基建负责提供完整的执行数据，是其他模块能够正常工作的基础。

### 1.2 三种核心能力：系统需要做到什么？

四个模块最终需要形成三种能力。

<div class="table-scroll" role="region" aria-label="能力、需要回答的问题、主要承载模块（可横向滚动）" tabindex="0">

| 能力 | 需要回答的问题 | 主要承载模块 |
|---|---|---|
| 发现问题 | 哪里出了问题？什么时候出现的？ | 在线评测与监控 |
| 定位问题 | 为什么出现问题？是哪一层的问题？ | Case 挖掘与归因、观测基建 |
| 驱动演进 | 修改之后是否真的变好了？有没有引入新的问题？ | 离线评测、在线评测 |

</div>

三种能力是递进关系。

首先，需要通过线上和离线数据发现异常；然后通过 Case 和 Trace 还原执行过程，找到问题根因；最后通过 Agent 优化和评测回归验证修改是否有效。

如果缺少发现能力，问题只能依赖用户投诉；如果缺少定位能力，团队只能反复尝试；如果缺少验证能力，修复一个问题可能又引入两个新问题。

### 1.3 两条 Loop：系统如何持续运转？

理想的评测体系不是一条单向流程，而是两条共享线上真实样本、相互反馈的循环。

**第一条：评测体系迭代 Loop**

线上评测和监控持续产生异常信号，经过 Case 挖掘与归因后，判断现有评测体系是否存在不足。

- 如果评测集没有覆盖该类问题，就补充新的评测样本。
- 如果现有评价标准不准确，就调整 Metrics 和 Rubric。
- 如果原有评测集已经无法代表当前业务，就重新检查样本分布和覆盖情况。

这条循环的目标是让评测体系不断接近真实业务需求。

**第二条：Agent 迭代 Loop**

同样的线上样本，经过 Case 归因后，如果确认问题来自 Agent 本身，就进入另一条优化路径。

例如，问题可能来自 Prompt、Skill 路由、知识检索、上下文管理、模型理解或工具调用。

研发根据根因进行修改，再使用评测集进行回归验证，通过后进入灰度或 A/B 测试，观察真实业务表现。

这条循环的目标是让 Agent 能力持续提升，同时避免牺牲已有能力。

两条 Loop 的连接点有两个：

第一是 Case 挖掘与归因。相同的 Bad Case 可能指向 Agent 本身的问题，也可能说明评测体系存在不足，需要先判断问题性质。

第二是评测资产。评测体系迭代的产出是更完善的评测资产，而这些资产又会提高 Agent 回归测试的覆盖率和发布门禁价值。

随着历史问题不断进入回归集，Agent 每次变更都需要通过更多经过验证的检查项，减少已知问题再次出现的概率。

### 1.4 一套评测资产：系统最终沉淀什么？

评测资产不应该只被理解为一份测试数据，而应该包含两类核心内容。

**评测标准**

- Metrics：明确需要衡量哪些能力和质量维度。
- Rubric：明确每个维度应该如何判断。

**评测样本**

- Golden Set（黄金集）：沉淀经过验证的高质量样本，定义合格表现。
- Regression Set（回归集）：记录历史问题，防止已修复的问题再次出现。
- Challenge Set（挑战集）：覆盖复杂、边界和长尾场景，检验能力边界。

每个评测样本还需要保留输入、预期行为、评价标准及其来源，确保后续能够复现和回归。

对于招投标筛选 Agent，评测资产不仅需要记录项目是否符合筛选条件，还需要保存对应的字段、主体、原文证据以及最终筛选依据。

**因此，评测资产既是 Agent 优化的验证依据，也是评测体系自身演进的产出。**

## <span class="chapter-number">02.</span> 评测资产与基础能力建设

评测系统的建设不应该从复杂的自动化平台开始，而应该先明确什么样的结果才算合格，并将其转化为能够执行的评测任务。

### 2.1 从业务目标构建评测标准

以招投标机会智能筛选系统为例，系统需要从多平台公告及附件中提取项目信息，并依据三项业务条件进行级联筛选：

1. 项目总投资额是否达到预设门槛。
2. 项目性质是否属于目标房屋建设类项目。
3. 企业性质是否符合国企、上市公司等目标条件，作为项目回款风险的参考信号。

需要注意，项目总投资额、招标控制价、合同金额和单个标段金额是不同字段；项目业主、招标人、建设单位和施工企业也可能是不同主体，不能简单混为一谈。

因此，评测不能只判断模型是否提取出了一个金额或企业名称，还需要判断字段语义、主体关联及原文证据是否正确。

可以将评测指标分为三个层次：

<div class="table-scroll" role="region" aria-label="评测层次、核心指标、具体判断（可横向滚动）" tabindex="0">

| 评测层次 | 核心指标 | 具体判断 |
|---|---|---|
| 字段提取 | 字段正确性、实体关联准确性 | 金额、项目类型、企业性质是否正确，是否对应正确主体 |
| 证据质量 | 证据一致性、Evidence Recall@K | 是否找到支持字段判断的原文证据 |
| 业务结果 | 筛选准确率、误筛率、漏筛率 | 最终保留和淘汰的项目是否符合业务条件 |

</div>

此外，还需要关注工具调用合理性、附件解析触发率、任务完成率和执行成本等过程指标。

### 2.2 将评测标准转化为可执行 Task

一个评测指标不能直接等同于一个评测样本。

需要将实际业务问题转化为具有固定输入、预期结果和明确评价标准的 Evaluation Task。

例如，针对项目总投资额与招标控制价容易混淆的问题，可以设计以下评测任务：

<div class="table-scroll" role="region" aria-label="Task、组成、具体内容（可横向滚动）" tabindex="0">

| Task 组成 | 具体内容 |
|---|---|
| 输入 | 招标公告及对应附件 |
| 目标字段 | 项目总投资额 |
| 预期结果 | 正确提取项目总投资额，而不是招标控制价或标段金额 |
| 证据要求 | 提供对应原文片段、文档位置及字段所属主体 |
| 评价标准 | 字段值正确、字段类型正确、主体关联正确、证据能够支撑判断 |

</div>

一个完整 Task 还需要记录数据版本、模型版本、Prompt 版本及预期行为，确保后续可以重复执行。

可以将其组织成如下结构：

```yaml
task_id: tender_amount_001

input:
  announcement_id: example_001
  documents:
    - document_id: attachment_001
      version: v1

expected:
  field: project_total_investment
  value: "由人工标注的预期值"
  entity: "对应的项目主体"
  evidence:
    document_id: attachment_001
    location: "对应章节或页码"

evaluation:
  - field_correctness
  - field_type_correctness
  - entity_consistency
  - evidence_consistency
```

以上是建议采用的评测 Task 结构示意，并非项目现有数据格式。

### 2.3 评测集如何组织

评测集可以按照两个维度组织。

**第一维度：按照评测视角区分。**

- 端到端评测集：判断最终筛选结果是否符合业务要求。
- 过程评测集：判断公告解析、附件检索、字段提取、主体关联和工具调用是否正确。

**第二维度：按照评测用途区分。**

- Golden Set：保留字段提取和项目筛选正确的代表性样本。
- Regression Set：记录历史出现过的字段错配、检索遗漏和错误淘汰。
- Challenge Set：覆盖金额多义、多个主体、跨章节证据和复杂附件等场景。

这两个维度并不冲突。例如，可以同时存在端到端回归集和字段提取回归集。

评测集不应该一开始就拆分得非常细。

更合理的顺序是先覆盖核心业务场景和关键执行环节。当出现「知道最终结果错误，却无法判断具体哪个环节出了问题」时，再进一步拆分过程评测集。

### 2.4 建立最小观测能力

评测资产负责定义判断标准，观测基建则负责提供实际执行数据。

在项目中，一次筛选任务可能经历公告采集、正文解析、附件获取、OCR、混合检索、字段提取、规则校验和最终筛选。

如果只记录最终筛选结果，就无法判断错误发生在哪个环节。

因此，至少需要记录：

<div class="table-scroll" role="region" aria-label="数据类型、需要记录的内容（可横向滚动）" tabindex="0">

| 数据类型 | 需要记录的内容 |
|---|---|
| 原始数据 | 公告来源、采集时间、公告及附件版本 |
| 文档处理 | OCR 状态、切块结果、章节与页码 |
| 检索过程 | BM25 和向量检索结果、召回片段、Reranker 排序 |
| 模型调用 | 模型版本、Prompt 版本、输入输出 |
| 字段校验 | 候选字段、关联主体、规则判断结果 |
| 流程执行 | LangGraph 节点、状态变化、工具调用、重试记录 |
| 最终结果 | 筛选结果、淘汰原因、证据引用 |
| 运行信息 | Token、耗时、异常状态、任务 ID |

</div>

在建设初期，不需要一次性完成所有埋点。首先保证能够通过 Trace 还原一次 Bad Case，再根据后续诊断需求补充观测数据。

**本章的最终产出是：第一版评测标准、可执行 Task、分层评测集，以及能够支撑问题复现的最小观测能力。**

## <span class="chapter-number">03.</span> 离线评测：建立质量基线与发布门禁

完成评测资产建设后，下一步是建立稳定的离线评测机制。

离线评测的核心作用，是在 Agent 发生变更之后，验证新版本是否解决了原有问题，以及是否引入了新的退化。

### 3.1 评测什么：从最终结果到执行过程

对于招投标筛选 Agent，建议同时建立两类评测。

**端到端评测**

站在业务视角，判断最终筛选结果是否正确。

例如，某项目是否同时满足投资额、项目性质和企业性质三项条件，系统是否正确保留或淘汰。

这里需要重点关注：

- 误筛率：不符合条件的项目被错误保留。
- 漏筛率：符合条件的项目被错误淘汰。
- 最终筛选准确性：结果是否符合业务规则。
- 证据完整性：每个关键判断是否有对应依据。

**过程评测**

站在系统执行视角，判断每个关键环节是否正确。

<div class="table-scroll" role="region" aria-label="评测模块、具体评测内容（可横向滚动）" tabindex="0">

| 评测模块 | 具体评测内容 |
|---|---|
| 数据采集 | 公告是否完整采集，附件是否正确关联 |
| 文档解析 | OCR 是否成功，关键章节是否被正确提取 |
| 检索 | 是否召回正确的字段证据 |
| 字段提取 | 金额、项目类型、企业性质是否正确 |
| 主体关联 | 字段是否对应正确的招标人或项目主体 |
| 规则判断 | 级联筛选是否按照业务条件执行 |
| 工具调用 | 是否合理触发附件解析、重试和其他工具 |

</div>

端到端评测回答「项目筛选是否正确」，过程评测回答「哪个环节导致筛选结果错误」。

### 3.2 固定评测环境：保证版本对比可信

回测的本质是控制变量对比：只让 Agent 版本变化，其他条件尽可能保持不变，这样才能将结果差异归因到版本变更。

对于招投标系统，需要固定：

- 招标公告和附件的数据快照。
- 文档解析与 OCR 版本。
- 知识切块和检索配置。
- 模型与 Prompt 版本。
- Reranker 及规则引擎配置。
- 投资额门槛和其他筛选条件。

如果评测时使用的公告数据、知识版本或执行环境发生变化，即使最终结果不同，也无法判断究竟是系统变更导致的，还是输入和环境发生了变化。

另外，大模型输出存在一定随机性，同一个 Task 多次运行可能产生不同结果。因此，对于重要评测任务，不应该只依赖一次实验的结果，而应通过多次运行观察整体通过情况和输出稳定性。

对于需要调用外部数据的任务，还应尽量固定接口返回结果，或者使用可复现的模拟数据，避免第三方服务波动干扰评测。

### 3.3 分层门禁：让评测真正约束版本发布

不是所有 Rubric 都同等重要，应该根据业务风险设置不同的发布标准。

<div class="table-scroll" role="region" aria-label="指标等级、典型指标、发布策略（可横向滚动）" tabindex="0">

| 指标等级 | 典型指标 | 发布策略 |
|---|---|---|
| 核心门禁 | 关键字段正确性、证据一致性、筛选结果正确性 | 一票否决或设置严格最低通过率 |
| 质量门禁 | 检索效果、主体关联、工具调用合理性 | 设置最低通过阈值 |
| 体验与效率指标 | Token 消耗、执行耗时、附件解析率 | 设置合理的目标范围和波动阈值 |

</div>

例如，优化检索策略后，Evidence Recall@5 提升，但字段主体关联准确性下降，就不能仅凭检索指标改善认定新版本更好。

对于核心门禁，即使其他指标得分很高，只要出现不可接受的业务错误，也应该阻断发布。

同时，评测不能只停留在人工执行和查看报告的阶段，而应该接入研发和发布流程。

例如，当 BM25 与向量检索权重发生调整时，自动运行对应的检索评测集和端到端回归集；当模型或 Prompt 发生变更时，触发相关核心样本的回归测试。通过后才能进入灰度或正式发布，未通过则返回问题分析与优化环节。

可以根据变更范围执行不同规模的评测：

- 日常代码或配置变更：优先执行核心回归集。
- 重要模块变更：执行相关过程评测和完整回归集。
- 重大版本发布：执行完整评测集，并检查所有核心门禁。

**没有接入研发流程的门禁，本质上只是一个建议。只有当评测结果能够真正影响发布决策时，回归测试才具备持续的质量约束力。**

我的理解是，离线评测不是为了证明新版本的分数更高，而是为了证明每一次变更都在可控范围内，并且没有以牺牲已有能力为代价。

## <span class="chapter-number">04.</span> 在线评测与监控：建立真实业务反馈入口

离线评测只能验证已有样本，无法覆盖所有真实公告、复杂附件和新的项目类型。

因此，Agent 上线后还需要持续收集真实运行数据，让线上反馈成为评测资产更新的重要来源。

### 4.1 在线评测的三种方式

<div class="table-scroll" role="region" aria-label="方式、主要用途、实际应用（可横向滚动）" tabindex="0">

| 方式 | 主要用途 | 实际应用 |
|---|---|---|
| 影子模式 | 使用真实流量验证新版本，不影响实际筛选结果 | 验证新检索策略 |
| A/B 测试 | 对比不同版本在真实任务中的表现 | 比较不同字段提取策略 |
| 线上巡检 | 周期性抽样检查真实运行结果 | 人工复核筛选结果与证据 |

</div>

三种方式承担不同职责：

影子模式适合上线前验证，A/B 测试适合比较不同版本的业务效果，线上巡检则负责持续观察系统质量。

### 4.2 在线评测与在线监控的区别

两者关注的重点不同：

- 在线评测关注：Agent 是否正确完成了筛选任务？
- 在线监控关注：系统是否正常运行？

例如，检索工具调用成功率达到 100%，并不代表召回的证据一定正确。

如果系统每次都成功调用了检索工具，却持续召回错误主体对应的金额，那么监控指标可能正常，但评测结果依然不合格。

建议从三个维度建立线上监控：

<div class="table-scroll" role="region" aria-label="监控维度、重点指标、监控目的（可横向滚动）" tabindex="0">

| 监控维度 | 重点指标 | 监控目的 |
|---|---|---|
| 可用性 | 采集成功率、工具失败率、超时率、解析失败率 | 发现系统运行异常 |
| 成本 | Token 消耗、平均耗时、附件解析率、单任务成本 | 发现资源消耗异常 |
| 行为变化 | 项目类型分布、附件触发率、任务数量分布、筛选结果分布 | 发现业务场景变化 |

</div>

其中，行为监控尤其重要。

例如，某段时间复杂附件的比例明显增加，原有评测集却主要由正文即可完成判断的公告构成，那么即使原有离线评测全部通过，也可能无法反映当前系统的真实表现。

### 4.3 巡检：连接在线评测与监控

线上巡检同时具有质量评测和异常监控两种属性。

一种实用的方式是从离线评测集中抽取一部分代表性 Task，周期性地使用线上 Agent 执行，并与人工标注结果或预期结果进行比较。

随着评测集不断扩充，也可以单独维护一套线上巡检集。

例如：

- 每日抽取一定数量的项目，复核投资额字段及其证据。
- 对复杂附件、多金额和多主体任务提高抽样比例。
- 对出现异常的任务增加定向复核。
- 保留一定比例的随机样本，发现未知问题。

巡检的结果不仅用于判断线上质量是否稳定，还需要记录异常样本、对应指标和执行 Trace，供后续 Case 挖掘与归因使用。

### 4.4 如何从线上数据产生 Case

线上巡检可以结合固定评测集和真实任务抽样：

- 对高风险字段和最终筛选结果进行重点抽样。
- 对异常指标对应的任务进行定向抽样。
- 对复杂附件和多主体场景增加抽样比例。
- 对正常运行的任务保留随机抽样，避免只关注已知问题。

最终将线上真实样本及其执行记录送入 Case 池。

**本章的核心产出是：线上质量信号、运行监控数据和待分析的真实案例。**

## <span class="chapter-number">05.</span> Case 挖掘与归因：驱动双循环演进

Case 挖掘与归因是整个系统中最重要的连接环节。

它负责把线上产生的异常信号转化为具体问题，并判断这些问题最终应该进入 Agent 优化，还是评测体系优化。

### 5.1 Case 从哪里来？

Case 主要来自四个渠道：

<div class="table-scroll" role="region" aria-label="来源、作用、实际案例（可横向滚动）" tabindex="0">

| 来源 | 作用 | 实际案例 |
|---|---|---|
| 用户反馈 | 收集人工复核或业务使用中的问题 | 发现符合条件的项目被错误淘汰 |
| 指标异常 | 根据评测和监控发现异常 | 某类金额字段正确率下降 |
| 业务规则 | 根据已知风险筛选特定场景 | 同时出现总投资额、控制价和标段金额 |
| 随机抽样 | 发现尚未被现有指标覆盖的问题 | 抽查正常结果，发现主体关联错误 |

</div>

四种来源需要结合使用。

只依靠用户反馈，容易遗漏没有被主动报告的问题；只依靠监控，只能发现已经被指标定义的异常；而随机抽样能够帮助团队发现尚未意识到的质量风险。

### 5.2 Good Case 与 Bad Case 的沉淀

收集到的样本需要经过清洗、分类和确认。

- Good Case：经过验证的正确筛选结果，可以沉淀到黄金集。
- Bad Case：存在明确问题的样本，完成归因后可以进入回归集。
- Challenge Case：复杂金额、多主体、跨章节证据等场景，用于检验能力边界。

这里并不是所有 Bad Case 都应该直接进入回归集。

如果样本本身存在歧义，或者业务标准尚未明确，就需要先完成确认，否则反而会给评测集引入噪声。

### 5.3 如何通过 Trace 定位根因

可以先按归因层级区分问题，再结合具体执行链路确认修复方向与责任分工。

假设某份招标公告及其附件中同时出现项目总投资额、招标控制价和单个标段金额，Agent 将招标控制价错误提取为项目总投资额，最终导致项目筛选结果错误。

这时不能直接认为是模型能力不足，而应该结合执行过程进行分析。

<div class="table-scroll" role="region" aria-label="排查环节、需要确认的问题、可能的根因（可横向滚动）" tabindex="0">

| 排查环节 | 需要确认的问题 | 可能的根因 |
|---|---|---|
| 数据采集 | 是否获取了正确公告及附件？ | 数据缺失或附件关联错误 |
| 文档解析 | 是否完整提取了相关章节？ | OCR 或解析遗漏 |
| 文档切块 | 相关金额及其说明是否被切分到不同片段？ | 切块粒度不合理 |
| 知识检索 | 是否召回了对应字段的证据？ | BM25 或向量检索遗漏 |
| 重排序 | 正确证据是否被排在候选结果之后？ | Reranker 排序问题 |
| 字段提取 | 是否区分总投资额与招标控制价？ | Prompt 或模型理解问题 |
| 主体关联 | 金额是否对应正确的项目主体？ | 实体关联错误 |
| 规则判断 | 是否使用了正确字段进行投资额筛选？ | 规则映射错误 |

</div>

这里的关键是：评测指标只能反映问题现象，Trace 才能帮助我们还原执行过程。

例如，Evidence Recall@5 下降，可以优先检查检索和重排序；如果证据召回正常，但字段正确性下降，则应该进一步检查字段语义理解和主体关联。

### 5.4 从问题现象到根因验证

找到可疑环节之后，还不能直接认定它就是根因。

更合理的做法是提出具体假设，并通过针对性验证确认。

例如：

**假设：** 招标控制价被错误提取为项目总投资额，是因为检索结果缺少字段对应的章节上下文。

可以依次验证：

1. 检查原始文档，确认是否存在完整的金额定义。
2. 检查切块结果，确认字段名称与金额是否被分离。
3. 检查 BM25、向量检索和 Reranker 的候选结果。
4. 在固定样本上仅调整切块策略，观察字段正确性是否改善。
5. 使用原有回归集验证是否引入其他退化。

如果仅调整切块策略后目标问题得到改善，并且其他核心指标没有退化，就有了更充分的证据支持这一优化方向。

这里需要避免同时修改切块、检索、Prompt 和模型，否则即使最终指标改善，也无法判断是哪项变更真正起作用。

### 5.5 Case 如何反哺评测资产与 Agent

归因之后，需要判断问题究竟属于 Agent 本身，还是评测体系自身。

<div class="table-scroll" role="region" aria-label="归因结果、应采取的动作、评测资产变化（可横向滚动）" tabindex="0">

| 归因结果 | 应采取的动作 | 评测资产变化 |
|---|---|---|
| 字段提取错误 | 优化 Prompt 或字段提取逻辑 | 将确认后的错误样本加入回归集 |
| 检索证据遗漏 | 优化切块、混合检索或 Reranker | 补充检索评测样本 |
| 主体关联错误 | 优化实体识别和关联校验 | 补充多主体挑战样本 |
| 规则判断错误 | 修正规则映射和筛选逻辑 | 补充端到端回归样本 |
| 新业务场景未覆盖 | 扩展评测场景 | 新增评测 Task |
| Rubric 无法准确判断 | 校准评价标准 | 更新 Rubric |
| 原有指标无法衡量风险 | 增加评价维度 | 更新 Metrics |

</div>

需要区分三个概念：

- Metrics 更新：原有评价维度不足，需要增加新的质量衡量维度。
- Rubric 更新：评价维度存在，但具体判断标准不完整或不准确。
- 评测集更新：评价标准已经明确，但缺少能够验证该场景的样本。

这三种更新的目的不同，不能把所有问题都简单归结为增加评测样本。

从这里可以看到，评测资产有两个重要的反馈方向：

**向 Agent 反馈：** 通过回归测试验证优化结果，保证已有能力不发生退化。

**向评测体系反馈：** 通过新增样本和校准评价标准，让下一轮评测能够发现更多问题，并且判断得更加准确。

这也是为什么 Case 归因不能只停留在问题分类，而必须明确后续的资产更新和系统优化动作。

## <span class="chapter-number">06.</span> 从人工闭环到自动化评测系统

前面的流程说明了评测体系如何运行，但在实际项目初期，很多环节仍然依赖人工：

人工抽取 Case、人工判断问题、人工补充评测集、人工修改 Agent，再人工执行回归。

当 Agent 的任务量和业务场景逐渐增加，这种方式会带来明显的效率瓶颈。

因此，后期建设方向应该是将前面的流程逐步自动化，让评测资产能够自动积累，让问题能够被自动发现和分析，并将经过验证的优化结果反馈到 Agent。

### 6.1 自动化评测系统的完整流程

可以将自动化建设拆成六个连续环节：

**第一步：自动发现。**

从用户反馈、线上指标、异常日志和随机抽样中获取 Case。

例如，自动收集投资额字段校验失败、附件解析异常以及人工复核不一致的任务。

**第二步：自动筛选。**

对原始样本进行去重、清洗、分类和结构化处理，关联公告、附件和 Trace。

同时检查样本是否完整，是否存在无法复现的输入或缺失证据。

**第三步：自动评估。**

利用规则引擎和 LLM Judge 识别字段错误、证据不一致、主体关联错误等问题。

其中，金额、字段类型、主体关联等可明确验证的内容优先采用规则或结构化比对；需要理解语义的部分再交给 LLM Judge。

**第四步：自动归因。**

结合 Trace 分析执行链路，生成可能的根因和优化方向。

例如，判断问题更可能来自 OCR、切块、检索、重排序还是字段提取。

这里的自动归因应该输出可验证的假设，而不是将模型生成的解释直接视为事实。

**第五步：自动更新与验证。**

将确认后的 Case 转化为候选评测 Task，更新回归集或挑战集；如果评价标准存在问题，则生成 Metrics / Rubric 的修改建议。

随后自动运行离线评测，验证 Agent 是否真正修复问题，以及是否影响其他能力。

**第六步：受控优化与发布。**

通过发布门禁后进入灰度或影子验证，持续观察线上表现。确认效果稳定后，再逐步扩大流量。

新的线上反馈继续进入 Case 池，形成下一轮循环。

### 6.2 自动化建设的三个阶段

并不是所有环节都应该直接交给 Agent 自主决定。可以按照自动化程度逐步建设。

<div class="table-scroll" role="region" aria-label="阶段、自动化能力、主要产出（可横向滚动）" tabindex="0">

| 阶段 | 自动化能力 | 主要产出 |
|---|---|---|
| 评测执行自动化 | 自动采样、运行评测、生成报告、触发回归 | 自动化评测流水线 |
| 问题分析自动化 | 自动发现异常、提取 Case、分析 Trace、生成归因假设 | 结构化 Case 与诊断报告 |
| 优化闭环自动化 | 生成评测 Task、提出 Agent 修改、自动验证和受控发布 | 自动化优化工作流 |

</div>

其中，需要保留明确的权限边界：

- Case 采集、去重和基础分类可以高度自动化。
- LLM Judge 可以辅助判断，但需要通过人工标注样本持续校准。
- 自动生成的评测 Task 需要验证字段、证据和预期结果。
- Metrics 和 Rubric 的重要变更需要业务人员确认。
- Agent 代码和规则修改需要经过回归测试。
- 涉及核心业务筛选逻辑的发布，需要保留人工审批或明确的发布门禁。

### 6.3 如何让评测资产真正实现自动积累

这是自动化系统中最值得关注的一点。

自动化不应该只是每天运行一次评测，然后输出一份报告，而是要让新发现的问题能够持续转化为有效资产。

例如：

1. 系统发现一个金额字段错配的 Bad Case。
2. 自动关联原始公告、附件和 Trace。
3. LLM 根据执行记录生成候选错误类型。
4. 系统提取对应的原文证据和预期字段。
5. 人工确认该样本确实存在字段错配。
6. 将其转化为可执行的 Regression Task。
7. 自动运行新旧版本回归，确认问题是否修复。
8. 将修复结果、版本和验证记录一起保存。

随着这样的过程不断重复，评测集就不再依赖人工一次性编写，而是逐渐从真实业务运行中积累。

但这里有一个必须守住的原则：

**自动生成不等于自动认可。**

如果错误的评测样本或错误的 Rubric 被直接写入评测资产，后续 Agent 就可能被持续优化成迎合错误标准的系统。因此，资产更新需要经过证据校验和必要的人工确认。

最终，自动化的目标不是让 Agent 随意修改自己，而是让系统能够自动发现问题、分析原因、生成候选优化方案、执行验证，并在满足条件后进入受控发布。

## 总结：让评测资产成为系统持续演进的驱动力

一套可持续演进的 Agent 评测系统，并不是简单地将离线评测、在线监控和 Trace 工具连接起来，而是要建立它们之间明确的数据流和反馈关系。

离线评测利用已有资产守住质量底线，在线运行不断产生新的真实样本，Case 挖掘与归因判断问题的性质，再将结果分别反馈给 Agent 系统和评测体系。

其中，评测资产承担着最重要的连接作用：

- 新的业务问题让评测集不断扩充。
- 评价偏差推动 Metrics 和 Rubric 持续校准。
- 历史 Bad Case 形成回归约束。
- 经过验证的 Good Case 帮助定义更高质量的目标。
- 更完善的评测资产进一步约束 Agent 的每次变更。

当这些环节逐步实现自动化，评测就不再是一个独立的测试流程，而是成为 Agent 持续运行和优化的基础设施。

**真正的自进化，不只是 Agent 能够根据反馈修改自己，而是整个系统能够持续发现问题、积累经验、校准评价标准，并通过验证后的结果推动下一轮优化。**
