# Agent Evaluation & Continuous Improvement
<p class="article-subtitle">从评测设计到持续优化的 Agent 评测方法论</p>

## 前言：为什么需要 Agent Evaluation？

随着 Agent 在实际业务中的应用越来越广泛，如何判断一个 Agent 是否真正可靠、有效地完成任务，逐渐成为系统建设中不可忽视的问题。

与传统的模型评测不同，Agent 的最终表现不仅取决于模型本身，还受到 Prompt、工具调用、知识检索、记忆管理和业务流程等多个环节的影响。单纯依靠模型回答的准确性，已经不足以判断整个系统的质量。

我更关注的是：如何定义评测标准、如何构建评测集、如何通过评测结果定位问题，以及如何让评测真正服务于 Agent 的质量优化。

---

## 01. 评测基础

### 1.1 Agent 不是一个模型，而是一个运行在真实系统中的系统

在讨论 Agent 评测之前，需要先明确一个问题：我们究竟在评测什么？

Agent 并不等于一个大语言模型。模型只是其中负责理解、推理和生成的核心组件。当模型被放入真实业务系统后，还需要与 Prompt、Skill、Tool、知识检索、记忆机制、状态管理和业务流程等模块协同工作，才能完成用户交付的任务。

因此，用户最终感受到的 Agent 表现，并不完全取决于模型本身，而是整个系统协同运行的结果。

这也意味着，Agent 评测不能简单理解为模型输出是否正确，而应该从整体系统出发，判断它是否能够稳定地完成用户任务，以及是否真正创造了业务价值。

基于这个特点，我倾向于将 Agent 评测拆成三个层次：

这三个层次实际上构成了一条从业务结果到技术能力的拆解链路：先明确业务需要什么，再确定 Agent 应该具备什么能力，最后判断底层模型是否能够支撑这些能力。

需要注意的是，三个层次之间存在依赖关系，但不能简单地将上层问题归因于下层。

例如，员工通过 AI 助手查询福利政策后，仍然需要反复向 HR 咨询，可能是 Agent 没有正确理解员工的个人情况，也可能是政策知识召回不完整、回答缺少必要的申请条件，甚至是模型本身的理解能力不足。

**评测的目的不是简单地给 Agent 打分，而是建立一套从业务价值到技术能力的可追踪判断体系。**

### 1.2 Agent 评测：客观评测与主观评测

明确评测对象之后，下一个问题就是：我们应该如何判断 Agent 做得好不好？

我认为，对于 Agent 来说，两种评测都不可缺少。

客观评测帮助我们建立质量底线，避免系统出现明显错误；主观评测则帮助我们判断 Agent 是否真正好用，决定它能够达到的质量上限。

以企业 AI 自助答疑项目为例，即使 Agent 能够准确检索到福利制度中的相关条款，也不代表员工一定能够理解自己的申请条件，更不代表员工已经知道下一步应该准备什么材料。

如果只关注客观指标，Agent 可能最终只是一个能够正确引用制度、但无法真正帮助员工解决问题的系统。反过来，如果只有主观评价，又很难稳定地发现问题、衡量版本变化。

因此，需要先通过主观评测明确「什么是好的结果」，再通过客观评测和过程指标，建立能够持续验证和优化的机制。

## 02. 如何设计主观评测

主观评测最大的难点在于，很多评价本身没有唯一正确答案。

例如，我们开发了一个企业 AI 自助答疑 Agent，希望它能够根据企业制度和 FAQ，回答员工关于福利政策、申请条件和办理材料的问题。

这时，如果只判断回答是否包含正确的政策条款，显然是不够的。

一个回答即使引用了正确的制度，也可能存在解释不清楚、没有结合员工实际情况、遗漏申请条件、材料清单不完整，或者反复询问员工已经提供过的信息等问题。

那么，如何把这些模糊的评价转化为可以实际执行的评测指标？

我认为主要有四个步骤。

### 2.1 由具备业务经验的人定义评价标准

主观评测的起点应该是业务，而不是技术。

以企业福利答疑 Agent 为例：

什么样的回答才算真正解决了员工的问题？什么叫解释清楚？什么情况下需要追问？什么情况下应该转人工？

这些问题很难通过通用的语言模型能力直接定义，需要由熟悉企业福利政策、员工服务流程以及 HR / 行政业务的人参与决策。

例如，员工询问「我现在可以申请这项福利吗？」

一个好的回答不应该只是复述制度，而应该结合员工提供的信息，说明：

- 当前是否符合申请条件；
- 判断依据来自哪一条企业制度；
- 如果信息不足，还需要补充什么；
- 如果符合条件，需要准备哪些材料；
- 如果涉及特殊认定或审批，应该由谁进一步处理。

因此，首先需要组织具备业务经验的评审人员，对什么样的回答能够真正解决员工问题达成共识。

这里有一个重要概念：**Inter-rater Reliability（评审者间一致性）**。

也就是不同评审人员面对同一份回答时，是否能够得出相近的判断。

如果一个 HR 认为回答已经解决了员工的问题，另一个 HR 却认为缺少关键申请条件，那么问题可能并不在 Agent，而在于我们对「回答完整」的定义还不够清晰。

因此，主观评测不是让大家凭经验打分，而是要把业务经验转化成团队能够共同执行的评价标准。

### 2.2 指标下钻：把抽象评价拆解成具体判断项

以企业福利答疑 Agent 为例，假设我们最初只有一个评价指标：

「Agent 是否真正解决了员工的问题？」

这个指标过于宽泛，不同评审人员可能会关注不同的方面。

因此，需要继续拆解：

| 一级评价维度 | 二级判断项 | 具体判断标准 |
|---|---|---|
| 回答质量 | 政策解释准确性 | 是否正确解释企业制度，没有曲解政策 |
| 回答质量 | 依据支撑 | 是否提供正确的制度条款或 FAQ 依据 |
| 条件判断 | 适用条件完整性 | 是否覆盖申请资格、时间、适用范围等必要条件 |
| 交互质量 | 追问必要性 | 是否只询问判断所必需的信息，避免重复追问 |
| 办理指引 | 材料完整性 | 是否列出申请所需材料，有无遗漏 |
| 办理指引 | 操作清晰度 | 是否明确告知员工下一步应该怎么做 |
| 风险控制 | 边界处理 | 是否正确识别特殊认定、审批及无法确认的情况，并转人工 |

这里需要注意一个问题：并不是所有评价维度都适合直接设计成一个客观数值指标。

例如，「政策解释是否清楚」并不存在一个天然可计算的清晰率。它更适合被定义为一个 Rubric 评价项，再根据具体标准进行判断。

比如：

- 通过：准确解释适用政策，明确说明员工当前的申请条件和判断依据，表达清楚，没有重要信息遗漏。
- 不通过：仅复制制度原文，没有结合员工问题进行解释，或者遗漏了影响申请资格的关键条件。

对于更复杂的情况，可以设置 1–5 分的等级，并明确每个等级的判断依据。

这样，原本抽象的「回答是否清楚」，就被转化为可以被人工评审或 AI Judge 判断的具体标准。

### 2.3 如何选择真正有价值的指标？

指标下钻并不意味着指标越多越好。过多的指标不仅会增加评测成本，也容易让我们失去重点。

我认为，选择指标时主要考虑三个方面：

1. **业务相关性**：是否直接影响任务完成？例如，政策解释准确性、申请条件完整性和材料清单完整性都直接影响员工能否获得有效帮助；平均回答长度则只能作为辅助观察数据。

2. **可判断性**：是否有明确的评价标准？例如，是否遗漏必要申请条件，可以根据企业制度进行核对；而「回答是否足够好」则需要进一步拆解，不能直接交给 LLM Judge 判断。

3. **可行动性**：指标不达标后，能否帮助定位问题？例如，政策依据支撑率低，可以优先检查知识检索；申请条件完整性低，可以进一步检查政策解析和条件提取；重复追问率高，则需要检查上下文管理。

因此，可以将指标分为两类：

- **核心指标**：衡量业务结果和 Agent 的关键能力。
- **诊断指标**：帮助进一步定位问题，指导具体优化。

核心指标判断结果是否达标，诊断指标帮助我们理解为什么不达标。这样既能避免指标体系过于复杂，也能让评测真正服务于问题定位。

### 2.4 二元化与持续校准

在指标下钻之后，还需要尽可能减少评价标准的模糊空间。

对于能够明确判断的项目，可以采用 Yes / No 的二元方式。

例如：

- 是否引用了正确的政策依据？
- 是否遗漏了必要的申请条件？
- 是否列出了全部必需材料？
- 是否重复询问员工已经提供的信息？
- 是否对需要人工审批的情况进行了正确转接？

对于政策解释清晰度、交互体验等复杂维度，则可以保留分级评分，但必须明确评分标准。

完成指标定义之后，还需要通过实际案例不断校准。

例如，先由多名 HR / 行政业务人员对同一批回答进行独立评价，再比较评分结果。如果差异较大，就回到 Rubric 本身，检查是否存在定义不清、评价维度重叠或判断标准不一致的问题。

当人工评审逐渐达成一致之后，再将这些经过确认的案例用于校准 LLM-as-a-Judge，让模型按照同一套标准进行评价。

因此，主观评测的核心流程是：

**业务人员定义标准 → 指标下钻 → 二元化或分级 → 人工独立评审 → 校准一致性 → 持续迭代 Rubric。**

这样才能真正把模糊的「好不好」，转化为可重复、可比较、可执行的评价标准。

## 03. 如何通过客观评测定位问题

主观评测能够帮助我们判断 Agent 的结果是否符合业务预期，但当某个评价指标持续不达标时，还需要进一步找到背后的原因。

这里需要明确：**评测指标反映的是问题现象，不一定直接代表问题根因。**

例如，政策解释准确性不达标，并不意味着模型能力不足，也可能是企业制度没有被正确解析、知识没有被正确召回，或者 Prompt 没有准确传递适用条件。

因此，不能只根据最终评价结果直接修改某个模块，而应该建立一套从结果异常到问题定位的机制。

### 3.1 从结果指标到具体问题：先确定哪里不达标

假设我们开发了一个企业 AI 自助答疑 Agent，经过一段时间的使用和人工评审，发现以下指标表现：

| 评价指标 | 评测结果 | 状态 |
|---|---:|---|
| 政策解释准确性 | 96% | 达标 |
| 政策依据支撑 | 94% | 达标 |
| 适用条件完整性 | 63% | 不达标 |
| 材料清单完整性 | 92% | 达标 |
| 追问必要性 | 90% | 达标 |

注：以上均为示例数据，用于说明问题定位过程。

从结果来看，Agent 能够正确解释政策，也能引用相关制度，材料清单和交互表现基本正常，但在申请条件判断上持续存在问题。

这时不应该直接更换模型或修改 Prompt，而是先进一步拆解「适用条件完整性」这个指标。

例如，将其拆分为：

- 申请资格：是否判断了员工是否属于政策适用人群？
- 时间条件：是否考虑了入职时间、申请期限等要求？
- 适用范围：是否考虑了员工所属部门、职级或其他适用范围？
- 前置条件：是否识别了申请之前必须满足的条件？

经过进一步评审，发现问题主要集中在时间条件和前置条件，而申请资格和适用范围的判断基本正常。

这样，问题就从一个笼统的「申请条件判断不完整」，缩小到了两个具体的异常维度。

这一步的目的，是先确认究竟是哪一类质量问题，而不是一开始就对整个 Agent 执行链路进行全面排查。

### 3.2 定向诊断：结合执行过程找到可疑环节

明确具体异常之后，才需要进一步检查 Agent 的执行过程。

仍然以申请条件遗漏为例，可以根据问题特征，优先检查与条件判断相关的模块：

| 诊断环节 | 检查内容 | 可能发现的问题 |
|---|---|---|
| 知识库解析与检索 | 是否完整解析并召回政策中的时间、前置条件？ | 制度分块不合理、关键信息遗漏、召回内容不完整 |
| Prompt | 是否明确要求识别并逐项核对申请条件？ | 指令不清晰、条件检查要求不完整 |
| 多轮上下文 | 是否正确保留员工已经提供的个人信息？ | 历史信息丢失、上下文传递错误 |
| 模型生成 | 是否能够正确理解并应用已经提供的条件？ | 信息齐全，但仍然遗漏或错误解释条件 |

例如，员工询问福利申请条件时，Agent 遗漏了制度中的入职时间限制。此时需要结合执行记录（Trace），检查政策知识是否被正确解析和召回、Prompt 是否要求逐项核对申请条件，以及模型是否正确使用了已有信息。

如果原始制度包含相关规定，但检索结果没有召回，问题可能在知识解析或检索环节；如果检索结果完整，但模型仍然遗漏，则需要进一步检查 Prompt 和模型的条件理解能力。

因此，不需要每次遍历所有模块，而应该根据不达标指标和具体失败表现，选择相关的诊断路径。

例如，材料清单完整性不达标，就优先检查材料要求的解析、召回和生成过程，而不是直接检查模型的整体推理能力。

**指标负责缩小问题范围，Trace 负责还原执行过程，帮助我们找到值得进一步优化的环节。**

### 3.3 不要一看到指标差，就同时改所有东西

这是实际优化过程中很容易出现的问题。

当最终结果不好时，同时修改模型、Prompt、知识库、检索策略和工作流，看似能够快速尝试多种优化方向，但即使最终效果变好了，也无法判断究竟是哪一项改动起了作用。

更合理的方式是：先通过结果指标找到异常维度，再结合执行过程缩小排查范围，明确需要优化的模块。

修复之后，还需要重新运行原有评测集，观察目标指标是否改善，以及其他指标是否出现退化。

例如，针对申请条件遗漏问题，优化知识分块和检索策略之后，不仅需要重新检查适用条件完整性，也要确认政策解释准确性、依据支撑和其他场景的表现没有受到影响。

因此，整个定位过程可以总结为：

**指标发现异常 → 指标下钻 → 定向过程诊断 → 针对性优化 → 全量回归。**

这套机制并不要求每次都检查所有模块，而是让每一次优化都有明确的问题来源和验证依据。

## 04. 让评测体系先跑起来

Agent 评测是一门实践科学。**起步阶段，「让数据飞轮高效运转起来」的意义远大于「设计一个复杂精妙的评测体系」。评测体系不是一蹴而就的，而是依靠 Good Case 和 Bad Case 不断积累和完善的。**

初期不需要追求完整的指标体系和庞大的测试集，而应该从核心业务场景出发，先建立能够运行的最小评测体系（Evaluation MVP）。

### 4.1 如何快速构建最小评测集？

我建议初期至少准备三类内容。

**第一，一批核心业务任务。**

优先覆盖最常见、最重要的业务场景。

例如，企业 AI 自助答疑 Agent 可以先准备：

- 福利政策查询：员工询问某项福利的申请时间、适用范围和政策要求。
- 申请条件判断：员工提供自己的入职时间、所属部门等信息，判断是否满足申请条件。
- 办理材料指引：员工询问申请需要准备哪些材料、如何提交。
- 信息不足场景：员工只提供部分个人信息，需要 Agent 按需补问。
- 异常与边界场景：制度没有明确规定、政策存在冲突，或者涉及特殊认定和人工审批。

不需要一开始就准备几百甚至几千条数据。先选择二三十条具有代表性的高质量样本，就可以启动第一轮评测。

**第二，一套核心 Rubric。**

不要试图一开始就覆盖所有主观评价维度。

先选择最重要的几个：

- 政策解释是否准确。
- 政策依据是否正确。
- 申请条件是否完整。
- 材料清单是否完整。
- 追问是否必要。
- 是否正确处理需要转人工的情况。

每个维度都需要明确判断标准，并保留人工评审结果。

**第三，几个关键客观指标。**

选择能够帮助发现问题的指标即可。

例如：

- 政策信息提取准确率。
- 知识召回率及关键条款覆盖率。
- 申请条件识别准确率。
- Tool / Skill 调用成功率（如果系统涉及工具调用）。
- 输出结构和政策引用格式合规率。

这三部分建立起来之后，就已经可以开展第一轮离线评测。

### 4.2 用 Good Case 和 Bad Case 喂养评测体系

评测集的积累不应该只依赖预先设计的测试题，更重要的是从真实业务中持续收集案例。

其中，**Bad Case 的价值往往更高，因为它最容易暴露 Agent 的能力边界和系统短板；Good Case 则帮助团队定义高质量完成任务的范式，明确什么样的结果才算真正好。**

因此，Agent 评测指标体系可以按照以下路径逐步建立：

1. **从高频核心场景起步**：先确定主要业务任务和少量关键指标，不追求一开始就覆盖所有情况。
2. **收集 Bad Case**：从生产环境中发现回答错误、条件遗漏、检索失败和交互异常等问题。
3. **沉淀 Good Case**：保留经过业务确认的优秀回答，明确高质量完成任务的标准。
4. **构建标准评测样本**：将 Good Case 和 Bad Case 补充输入、预期结果、评价标准及必要的执行信息，转化为可重复运行的评测数据。
5. **用评测结果指导优化**：根据问题定位结果，针对性调整 Prompt、Skill、检索策略、工作流或模型。
6. **持续从线上抽样**：将新的线上表现和问题重新纳入案例库，形成下一轮评测。

随着案例不断积累，评测集也会逐渐形成不同用途的资产：

- **Golden Set**：经过确认的高质量样本，用于衡量基本质量。
- **Regression Set**：历史错误案例，用于回归测试，防止相同问题再次出现。
- **Challenge Set**：复杂、边界和长尾场景，用于检验系统能力边界。

需要注意，Bad Case 不应该在出现之后就直接加入所有评测集，而是需要先完成清洗、归因和标准确认，确保样本本身具有明确的评测价值。

**评测体系不需要一开始就设计得多么完善，而是要让每一次真实使用都能留下有价值的数据，让每一次评测都能为下一步优化提供依据。**

## 05. 评测集质量与评测效率

评测集并不是样本数量越多越好。一套有效的评测集，既要能够覆盖真实业务场景，也要考虑实际运行中的成本与效率。

### 5.1 评测集的代表性：测试数据能否反映真实业务？

假设我们为企业福利答疑 Agent 准备了 100 条测试数据，其中 80 条是简单的福利政策查询，15 条是材料查询，只有 5 条是复杂的申请资格判断。

即使 Agent 的总体通过率达到 95%，也不代表它在所有业务场景中表现良好。简单问题占比过高，可能掩盖复杂场景中的质量问题。

因此，评测集需要关注三个方面：

- **场景覆盖度**：覆盖政策查询、资格判断、材料准备、多轮追问、特殊情况处理等核心业务。
- **难度与风险分布**：除了常规问题，还应包含信息不完整、条件冲突和需要人工介入的复杂场景，尤其不能忽略低频高风险问题。
- **分层评测**：按照业务场景、难度和风险等级分别统计结果，而不是只看总体通过率。

例如，可以分别统计政策查询、申请资格判断、材料准备和多轮追问的通过率，避免总体结果掩盖某个关键场景的质量问题。

此外，还需要区分开发集和测试集。开发集用于日常调整和验证，测试集尽量保持独立，避免反复使用同一批样本优化，导致评测结果失真。

### 5.2 评测成本与效率：如何选择合适的执行方式？

Agent 评测涉及模型调用、知识检索、工具执行和自动评价等环节。如果每次修改都运行完整评测，不仅增加成本，也会延长开发周期。

因此，可以根据评测目的，将执行方式分为四类：

| 评测方式 | 执行时机 | 主要目的 |
|---|---|---|
| 冒烟测试 | 每次代码或配置变更后 | 使用少量核心 Case，快速检查基本功能是否正常 |
| 回归测试 | 重要修改、提交或发布前 | 验证历史问题是否再次出现，已有能力是否退化 |
| 全量测试 | 重要版本或架构调整后 | 使用完整评测集，全面检查各场景和指标 |
| 线上评测 | 生产环境运行期间 | 通过真实 Trace 抽样或风险触发，监测实际表现 |

同时，不同指标可以采用不同的评价方式：明确的参数、格式和规则可以通过代码直接判断；政策准确性、回答完整性等语义问题则可以使用 LLM Judge 或人工评审。

线上评测也不必对每条请求执行所有复杂指标，可以根据业务风险和评测成本设置抽样策略，对资格判断、政策冲突等高风险场景优先保证覆盖。

**评测效率的核心不是减少评测，而是根据不同场景和风险，选择合适的评测范围与执行方式。**

最终，我们需要的不是规模庞大的测试集，而是一套能够真实反映 Agent 能力、覆盖关键业务场景，并且能够以合理成本运行的评测体系。

---

## 总结

Agent 评测不是单纯衡量模型回答得好不好，而是从业务目标出发，判断整个 Agent 系统是否能够可靠地完成任务。

一套可落地的评测方法，需要先明确评测对象和业务标准，再将抽象评价转化为可判断的指标，通过客观评测和执行过程追踪定位问题，并利用 Good Case、Bad Case 建立具有代表性的评测集。

真正重要的不是一开始就设计出多么复杂的评测体系，而是让评价标准有依据、评测结果可验证、问题能够被定位。

**评测的最终目的，不是得到一个分数，而是知道 Agent 为什么表现好或不好，以及下一步应该改进什么。**
